# 配置和定时任务

## 首次安装

将整个 `tibo-quota-monitor` 文件夹放入宿主的用户 Skill 目录。Codex 可使用 `~/.codex/skills/`；使用者的宿主若采用其他目录，遵循其安装机制。仓库内安装也可以，但私人运行记录始终位于仓库外。只需公开的这个文件夹，不导入任何人的运行目录。

用户请求“配置并启动”后：

1. 检查 Node.js 20+ 和 curl。运行 `node "<skill>/scripts/monitor.mjs" init`，保留返回的私人目录路径。
2. 引导用户在目标飞书群添加“自定义机器人”。如果采用自定义关键词，设置为 `Tibo额度提醒`；签名校验开启时也需要签名密钥。飞书机器人只用作通知出口。
3. 运行 `prepare-file` 并在本机文本编辑器打开返回的 `setup.txt`。用户只需在等号后填写 Webhook、可选签名，并把授权项从 `NO` 改为 `YES`；保存后运行 `import-file`。脚本导入成功会删除临时文档。Agent 不读取文档内容、`credentials.json`，也不在聊天中索要凭据。
   如果用户明确希望使用网页配置，在后台运行 `configure`，将返回的 `setupUrl` 打开给用户。页面只监听本机回环地址，十分钟超时。
4. 运行 `status` 确认配置已存在且 `notificationAuthorized=true`。用户填写授权后，请求启动涵盖向该机器人发送一条连接测试及后续额度提醒。
5. 运行 `probe` 核对当前数据源可达性，再运行 `collect` 建立成功采集记录；按主 Skill 分析并 `apply`，暂不发送正式提醒。若源失败，保留配置并报告具体错误，不创建看起来已正常工作的任务。
6. 运行 `test-notification`。成功后创建宿主定时任务，并读取返回结果确认创建成功。最后运行 `activate --schedule-id ID`。

## Codex 定时任务

使用宿主实际提供的 `automation_update` 等定时工具。按工具规则创建本地任务，默认复用当前聊天的周期任务；若已有保存的任务 ID，先检查并更新它。使用北京时间每小时第 15 分钟，用户明确指定的其他频率优先。

定时提示词只需要包含以下内容，用实际的 Skill 绝对路径替换占位符：

> 执行已安装的 $tibo-quota-monitor，Skill 路径为 <skill>/SKILL.md。本轮是已经配置并授权的本地定时监控。先查看 status，未启用则结束；按 Skill 执行采集、语义判断、去重与飞书通知，每轮最多 3 次采集与判断。恢复运行后续查停机期间可获取的历史，明确额度重置也补发并注明原文发布时间和本次推送时间。私人凭据由发送脚本读取，不在对话中展示。若 reportNextUsage=true，本轮结束后按 Skill 汇报一次截至统计时的 Token 用量并清除请求；否则没有新提醒或新故障时保持安静。采集失败不得报告为没有新帖。

提示词中不包含 Webhook、签名、个人项目内容或历史推文。任务仅在本机和 Codex 可用时运行；不创建常驻系统服务，不使用云端执行。时间设置通过宿主工具提交，不让用户手工编辑调度表达式。若当前宿主没有可用的定时任务能力，保留手动检查功能并明确说明，不伪造“已启动”。

将实际返回的任务 ID 交给 `activate`。这只是记录宿主创建结果，脚本不会自行创建任务。成功回报应包含检查频率、是否包含疑似预告、私人数据位置和测试提醒是否送达。

## 维护

暂停必须同时更新私人配置和宿主任务；更换飞书机器人后重新测试，配置程序会先暂停本地发送。已有待发送消息会保留，恢复前应告知用户将发送至新配置的机器人。

网络请求使用 curl，继承现有代理环境，不读取、复制或修改系统代理配置。后台任务访问数据源失败而浏览器可用时，先核对该任务的网络环境。不得复制浏览器 Cookie 或 Coding 软件登录凭据来绕过配置问题。

源码升级使用新公开包覆盖 Skill 代码，私人数据目录保持独立。升级前读现有版本并保留用户修改；不能用清空目录或强制覆盖来处理冲突。

参考：[飞书自定义机器人](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)、[Codex 定时任务](https://learn.chatgpt.com/docs/automations)。
